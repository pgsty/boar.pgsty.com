## The three domains

Boar manages PostgreSQL through three different operational authorities:

- direct SQL and PostgreSQL protocol behavior;
- Patroni REST/DCS semantics for HA clusters;
- Pigsty inventory and allowlisted lifecycle automation.

They cannot be flattened into one generic `exec` API. Each has different
identity evidence, idempotency, failure boundaries, risk, and verification.

But keeping three independent write paths is equally unsafe: policy, approval,
audit, and crash recovery drift apart, and an Assistant or legacy endpoint can
bypass the strongest lane.

## Decision

Provider semantics remain in typed Drivers. Resource, Capability, Plan, Policy,
Operation, and Audit are shared. Within a domain there is exactly one external
dispatch authority.

```text
Kernel step
   ├─ Patroni driver → REST / DCS / PostgreSQL verification
   ├─ PostgreSQL driver → typed SQL action / parameter verification
   └─ Pigsty driver → sealed argv / lifecycle postcondition
```

## Patroni

The in-repository public packages are the canonical implementation. Existing
`control.Plan/v1alpha1` becomes a typed driver payload; 19 CLI commands and
their differential oracle remain permanent. The adapter preserves behavior but
cannot call Patroni outside the Kernel Operation.

## PostgreSQL

Direct discovery produces Resource and Capability facts. Writes are action
specific—create index or parameter change—not arbitrary SQL strings. Parameter
plans know whether a change is dynamic, requires reload, or requires restart.

## Pigsty

Inventory import produces a Candidate Graph. Driver plans bind source digest,
cluster, hosts, limit, tags, and a closed extra-variable allowlist. Execution
is an argv call generated by reviewed code, never a GUI-provided command or
playbook.

## Migration and projection

Legacy routes may remain for compatibility and may receive Job projections.
Feature gates choose the single authority during cutover. They do not grant
permissions and cannot cause dual dispatch.

An old Job can point to the new Operation; it cannot own a second execution.

This rule governs mutation. Read-side collection may call PostgreSQL, Patroni,
or a configured metrics provider directly through bounded readers; ADR-023
explicitly gives Boar its own glanceable instruments and problem panels. That
does not create another write authority.

## Current implementation boundary

The repository contains Kernel runtimes for typed PostgreSQL writes, Patroni
actions, and Pigsty lifecycle work, plus compatibility adapters and legacy Job
projections. Which action appears in the Console still depends on current
Effective Capability and Policy. The product roadmap stages the user journeys:
v0.7 concentrates on the read-side cockpit, v0.8 on reversible gated changes,
and v0.9 on destructive Pigsty depth. The existence of a Driver therefore does
not claim that every action is already exposed in every UI or release.

## Result

The system shares governance and recovery while keeping domain-specific truth.
That balance is the core of “one control plane”: one meaning, not one
untyped mechanism.
